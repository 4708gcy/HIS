## 二、亮点一：登录安全体系（约2分钟，含演示）

### 讲解要点

登录安全这块，我主要做了三件事：

**第一，密码不是明文存储的。** 注册或修改密码时，系统生成16位随机盐值，然后用SHA-256对"密码+盐值"做1000次迭代哈希，最终存到文件里的格式是 `salt$hash`。用盐值是为了防彩虹表攻击，迭代1000次是为了增加暴力破解的时间成本。

**第二，密码比较用的是恒时比较。** 我没有用普通的字符串 `==` 比较，因为 `==` 在发现第一个不匹配字符时就会返回，攻击者可以通过测量响应时间逐字符猜测密码。我的实现是用 `volatile` 关键字修饰的XOR循环，逐位异或后再累加差异值，这样无论密码是否匹配，比较时间都是恒定的。

**第三，账户锁定机制。** 连续输错5次密码，账户自动锁定（`isAccountActive = false`），必须由管理员在"账号封锁管理"中手动激活，同时重置失败计数器。

**第四，登录密码隐藏输入。** 注册时密码是明文显示的，用户需要确认自己输入的内容；但登录时密码全部显示为 `*`，旁边的人看不到密码内容。这不是用 `cin` 实现的——标准输入函数要么回显明文、要么完全不回显（连 `*` 都看不到）。我的做法是调用Windows API `SetConsoleMode` 关闭行输入模式和回显模式，然后用 `ReadFile` 逐字符读取键盘输入。每读到一个可打印字符，就把它存进字符串、同时在屏幕上输出一个 `*`；遇到退格键就把字符串末尾删掉一个字符，同时用 `\b \b`（退格→空格→退格）把屏幕上的 `*` 抹掉。回车键结束输入。这样既隐藏了真实密码，又能让用户看到自己输了几位。

### 演示步骤

1. 选择"登录" → 选择任意角色 → 输入ID后观察密码输入界面：每敲一个键只显示 `*`
2. 用错误密码连续登录5次，观察提示：第5次后显示"账户已被锁定"
3. 再次尝试登录同一账户，系统直接提示账户不可用
4. 用管理员账号登录 → 选择"7. 账号封锁管理" → 选择对应角色 → 输入被锁定的ID → 选择"1. 激活账户"
5. 回到登录界面，该账户恢复正常

> **老师可能追问：** 为什么不用 `cin` 或者 `getpass`？——`cin` 会回显明文；`getpass` 在Windows上不可用，而且它的行为是完全不回显，用户连自己输了几位都看不到。用Windows API逐字符读取+手动输出 `*` 是最灵活的做法，还能自己处理退格键。

## 三、亮点二：医疗记录体系设计（约2分钟，含演示）

### 讲解要点

除了用户管理，系统中7类业务记录的结构体也是我设计并实现的：挂号（Registration）、看诊（Consultation）、检查（Examination）、住院（Hospitalization）、用药记录（MedicationRecord）、药品（Medicine）、床位（bedInfo）。这里我说两个设计决策。

**第一，记录之间通过ID字段串联成业务链。** 比如：挂号记录存了 `patientID` 和 `doctorID`；看诊记录在此基础上多了 `registrationID`，能回溯到是哪次挂号来的；检查记录又多了 `consultationID`，能追溯到是哪次看诊开的检查；用药记录同时关联了 `consultationID`、`doctorID`、`patientID`、`pharmacistID`；住院记录关联了 `consultationID`、`nurseID` 和 `bedNumber`。这样任何一条记录都能沿着ID往上游追溯，形成完整的医疗业务链条。

**第二，结构体内部用 `std::vector` 管理嵌套集合。** 比如看诊记录（Consultation）里面有 `vector<Prescription> prescriptions` 存处方列表，`vector<string> examinationList` 存计划检查项目，`vector<string> attachments` 存附件路径。用药记录里面有 `vector<MedicationLine> lines` 存药品明细，每条明细记录药品ID、名称、数量、单价。药品结构体有 `vector<string> aliases` 存别名。这些嵌套数据在持久化时用前缀标记行来保存——比如看诊记录下面会有多行 `PRESCRIPTION:medicineID,name,dosage,frequency,duration,note`，加载时按前缀识别并还原到对应的vector里。

**第三，每类记录都有独立的状态枚举和状态流转。** 比如挂号状态：已预约→已支付→已完成/已取消；看诊状态：待就诊→就诊中→已完成/已作废；检查状态：已下单→已支付→检查中→已完成→已报告/已作废；用药记录有两个维度的状态——审核状态（待审核/通过/拒绝/撤销）和支付发药状态（未缴费/已缴费/已发药/已退药）。住院状态：申请中→已缴费→已入院→已出院/已作废。这些状态在代码中全部用 `enum class` 定义，编译期类型安全，不会出现拼写错误或越界值。

**第四，费用计算统一放在User基类中。** 三种费用计算函数——挂号费按医生职称（实习10元到主任50元共5档）、检查费按检查项目名称（14种项目，2-30元不等）、住院费按病房类型乘天数（普通50/隔离100/VIP 200/ICU 500元每天，最少算1天）。这些函数定义在User基类里，所有角色都能调用，避免各模块各自算各自的导致规则不一致。

### 演示步骤

1. 用管理员登录 → 选择"2. 医疗记录管理" → 选择"全院" → 选择"1. 挂号记录" → 选择"1. 查看所有挂号" → 展示挂号列表（可以看到每条记录的ID、关联的患者ID、医生ID、状态、费用等字段）
2. 返回 → 选择"2. 看诊记录" → 选择"按ID查询" → 输入一条看诊ID → 展示看诊详情（可以看到主诉、诊断、处方列表、检查项目列表等嵌套数据）

> **老师可能追问：** 为什么用enum class而不是int常量？——enum class是强类型枚举，不会隐式转换为int，编译器会在编译期检查赋值是否合法。用int常量的话，写错一个数字编译器不会报错，运行时才会出问题。

## 五、亮点四：数据持久化与紧急保存（约1.5分钟，含演示）

### 讲解要点

系统的所有数据都存在txt文件里，启动时加载到内存链表，退出时写回。

**文件格式方面：** 我设计了一套CSV格式，每个结构体的字段用逗号分隔。嵌套数据（比如看诊记录中的处方列表、检查项目、附件）用前缀标记行来保存，比如 `PRESCRIPTION:` 开头的行是一条处方，`VITAL_SIGNS:` 开头的行是15项生命体征数据。空字段统一用 `#` 占位，避免CSV字段错位。每个文件最后一行是 `count:N`，记录当前ID计数器，保证下次启动时新ID不会和已有ID冲突。

**链表构建方面：** 加载时用头插法构建双向链表，每个节点的 `prev` 和 `next` 指针在插入时设置好。

**紧急保存方面：** 程序注册了 `SIGINT`、`SIGABRT`、`SIGTERM` 三个信号处理器。当用户按Ctrl+C或程序异常时，`emergencySave()` 会遍历所有链表写回文件。这里有个技术细节：因为新节点用头插法加入链表，会改变局部变量 `adminHead` 等的值，而信号处理器无法直接访问main函数里的局部变量。我的解法是用双重指针——全局定义 `static Admin **g_adminHead`，让它指向main里的 `adminHead` 变量的地址。这样无论头插法怎么改head，`emergencySave` 里解引用 `*g_adminHead` 拿到的始终是最新的链表头。

### 演示步骤

1. 用管理员添加一条记录（比如添加一个新医生）
2. 打开 `Data/UserData/DoctorChainData/doctor_users.txt`，翻到最后几行，展示新写入的数据（可以看到ID、姓名、密码哈希等字段用逗号分隔）
3. 回到程序正常退出
4. 重新启动程序，用管理员登录 → 查看医生列表 → 确认刚才添加的医生还在

> **老师可能追问：** 为什么不用数据库？——课程设计要求自己实现数据结构和文件读写，用数据库就失去了锻炼的意义。

## 六、架构设计总结（约1分钟）

最后快速过一下整体架构：

- **类继承体系：** `User` 基类包含公共字段（ID、用户名、密码哈希、盐值、登录状态等），`Admin`、`Doctor`、`Nurse`、`Pharmacist`、`Patient` 五个子类继承 `User`，各自扩展业务字段。不过角色的菜单分发没有用多态，而是在 `main()` 中用条件分支直接调用各角色的方法。
- **数据结构：** 12条双向链表（5类用户 + 7类业务记录），节点内嵌套的集合（处方列表、检查项目等）用 `std::vector` 管理。
- **ID体系：** 用户ID为6位数字，首位区分角色（0管理员、1医生、2护士、3药剂师、4患者），后5位递增。业务记录ID带类型前缀（reg/con/exa/mrd/hos/med），后面接6位数字。床位ID由科室代码、区域号、病房类型、病房号、床位号自动组合生成。

## 七、可能的追问与参考回答

### Q1: 为什么用链表而不是数组或vector？

12条链表在程序运行期间会频繁增删节点。链表的插入和删除是O(1)（头插法只需要改几个指针），不需要像vector那样搬移元素。而且链表节点在堆上分散分配，不会像数组那样需要预分配大块连续内存。

### Q2: 逻辑删除的缺点是什么？怎么处理？

缺点是数据文件会越来越大，因为"已删除"的记录仍然占用空间。当前设计中，逻辑删除的记录在遍历时会被跳过（检查 `isDeleted` 标志），所以不影响查询性能。如果要优化，可以定期做一次"压缩"——只把未删除的节点写回文件。

### Q3: SHA-256是你自己实现的还是调库？

我自己实现的，在 `SHA-256.h` 和 `SHA-256.cpp` 中。SHA-256算法的核心是把消息分块填充，然后进行64轮压缩运算。每一轮用到消息调度字、工作变量和6个逻辑函数（Ch、Maj、Σ0、Σ1、σ0、σ1）。实现过程中我对照了FIPS 180-4标准文档来验证每一步的正确性。

### Q4: 恒时比较的原理是什么？

普通字符串比较（`==`）在发现第一个不匹配的字符时就会返回false，攻击者可以通过大量测量响应时间来逐字符推断正确密码。恒时比较的核心是：用一个变量累加所有对应位置的异或结果，循环遍历完整个字符串后再判断。用 `volatile` 关键字防止编译器把循环优化掉或做短路求值。这样无论密码是否匹配，循环都会跑完，执行时间几乎相同。

### Q5: 双重指针具体怎么工作的？

在 `main()` 里，每个链表头是一个局部变量，比如 `Admin *adminHead`。注册信号处理器时，我定义了全局的 `static Admin **g_adminHead`，然后让它指向 `adminHead` 这个变量本身的地址（`g_adminHead = &adminHead`）。当头插法把新节点插入链表时，`adminHead` 的值变了（指向了新节点），但 `g_adminHead` 存的是 `adminHead` 的地址，这个地址没变。所以 `emergencySave()` 里 `*g_adminHead` 解引用后，拿到的是 `adminHead` 当前的值，也就是最新的链表头。

### Q6: 12个全局ID计数器为什么要传引用而不是用全局变量？

ID计数器在 `main()` 中定义为全局变量，但传引用给各模块函数是为了保证函数签名清晰——调用方能从参数列表直接看到这个函数会修改计数器。如果全靠全局变量隐式依赖，代码耦合度高，出了bug不好排查。

### Q7: 模板函数AccountManageGeneric是怎么避免代码重复的？

五种角色的账号管理逻辑完全一样：遍历链表 → 显示ID和状态 → 匹配目标ID → 激活或封锁。唯一的区别是链表节点类型不同。用模板函数 `template <typename UserType>`，编译器会为 `Admin`、`Doctor`、`Nurse`、`Pharmacist`、`Patient` 各生成一份特化代码，逻辑只写一遍。

## 附录：终端UI实现原理（供自读，非答辩内容）

以下内容供你自己理解，答辩时不需要展开讲。

### 菜单框线绘制

使用Unicode双线框字符绘制菜单边框：`╔═╗║╚═╝`。每行菜单项先用 `getDisplayWidth()` 计算实际显示宽度，再补齐空格到固定列宽，确保框线对齐。

### CJK宽度计算（`getDisplayWidth`）

中文字符在终端中占2列宽度，ASCII字符占1列。函数通过判断UTF-8首字节的高位来区分：
- `0x00-0x7F`：ASCII，宽1，占1字节
- `0x80-0xDF`：UTF-8两字节字符，宽2
- `0xE0-0xEF`：UTF-8三字节字符（中文在此范围），宽2
- `0xF0-0xF7`：UTF-8四字节字符（emoji等），宽2

函数返回的是"终端显示列数"，不是字节数。菜单绘制时用这个宽度来补空格，保证右侧框线对齐。

### 彩色输出

`printSuccess`/`printError`/`printWarning` 三个函数分别用Windows API `SetConsoleTextAttribute` 设置控制台前景色（绿/红/黄），输出完再恢复默认颜色。

### 信息卡片（`printInfoCard`）

固定50列宽度，标题行居中显示，每个字段一行，用 `─` 分隔。对齐方式：标签靠左，值靠右。

### 隐藏密码输入（注册明文 vs 登录隐藏）

系统中有两个密码输入函数，用途不同：

- **`inputPwdCheck()`**（注册时用）：调用 `std::getline(std::cin, pwd)`，用户能看见自己输入的密码明文。注册场景下用户需要确认密码内容，明文显示是合理的。
- **`inputHiddenPwdCheck()`**（登录/修改密码时用）：不用 `cin`，而是用Windows API实现逐字符无回显读取，具体步骤如下：

1. **关闭行输入和回显：** 调用 `GetConsoleMode` 获取当前控制台模式，然后用 `SetConsoleMode(hStdin, mode & ~ENABLE_LINE_INPUT & ~ENABLE_ECHO_INPUT)` 关闭两个标志。`ENABLE_LINE_INPUT` 关闭后，`ReadFile` 不再等用户按回车才返回，而是每读一个字符就返回一次；`ENABLE_ECHO_INPUT` 关闭后，用户按键不会自动回显到屏幕上。
2. **逐字符读取：** 用 `ReadFile(hStdin, &c, 1, &charsRead, nullptr)` 循环读取，每次读1个字节。
3. **回显 `*`：** 读到可打印字符（ASCII 32-126）时，把字符追加到密码字符串，同时 `std::cout << '*'` 输出一个星号，让用户知道自己输入了几位。
4. **处理退格：** 读到 `\b` 或 `127`（退格/删除键）时，如果密码字符串非空，就 `pwd.pop_back()` 删掉最后一个字符，同时输出 `\b \b`（光标左移一位→输出空格覆盖 `*`→再左移一位），视觉上就是 `*` 被删掉了。
5. **回车结束：** 读到 `\r` 或 `\n` 时跳出循环。
6. **恢复控制台模式：** 输入完成后，用 `SetConsoleMode` 把之前保存的 `mode` 值写回去，恢复正常输入行为。

为什么不用 `cin >>` 或 `_getch()`？——`cin >>` 会回显明文且需要按回车；`_getch()` 虽然可以逐字符无回显读取，但它是conio库的扩展函数，不是标准C++的一部分，跨平台兼容性差。`ReadFile` 是Windows API的标准做法，信号处理中的紧急保存也用了同一个API（因为 `cin` 在信号处理器中不安全），代码风格统一。

### 操作日志（`LogManager`）

单例模式，构造函数中根据当前日期生成日志文件路径 `Data/OperationLog/his_YYYY_MM_DD.log`。写日志前用 `std::mutex` 加锁，保证线程安全（虽然当前程序是单线程，但预留了扩展能力）。`logOperation()` 记录格式为：时间戳 | 用户ID | 角色 | 操作类型 | 操作详情。

## 附录二：密码加密原理详解（供自读，非答辩内容）

以下内容帮你彻底理解密码加密的每一步原理，答辩时如果老师深问可以从中取用。

### 一、为什么不存明文？

如果数据文件泄露，明文密码直接暴露。更危险的是，大多数人多个网站用同一个密码，一个系统被攻破会导致用户的其他账号也被牵连。所以密码必须经过"不可逆"的变换后再存储——验证时也只能拿用户输入重新算一遍，看结果是否一致，而不是"解密"存储的密码来比对。

### 二、SHA-256算法是什么？

SHA-256是NIST（美国国家标准与技术研究院）发布的密码散列函数，它接受任意长度的输入，输出固定的256位（32字节/64个十六进制字符）摘要。核心特性：

1. **不可逆**：从输出无法推算出输入。这不是加密（加密可以解密），而是散列（hash），只有单向。
2. **抗碰撞**：找不到两个不同的输入产生相同的输出。
3. **雪崩效应**：输入改1个bit，输出有约一半的bit会翻转。

算法流程（对应代码 `SHA256::hash()`）：

1. **填充（Padding）**：在原始数据后面追加 `0x80`，然后补 `0x00` 直到总长度 mod 64 = 56，最后追加8字节的原始数据长度（大端序）。填充后的数据长度一定是64字节的整数倍。
2. **分块处理**：每64字节（512位）为一个数据块，依次处理。
3. **消息扩展**：每个块的前16个32位字直接从数据取，后48个字通过 `EP0`、`EP1` 等函数从前面已知的字推导出来，扩展到64个字。
4. **64轮压缩**：初始化8个工作变量 `a-h`，进行64轮运算。每轮用到消息调度字 `w[j]`、常量 `K[j]`、以及 `CH`（选择函数）、`MAJ`（多数函数）、`SIG0`/`SIG1`（混合函数）六个逻辑函数。这些函数通过位运算（与、或、异或、右旋转）实现充分的混淆。
5. **累加输出**：64轮结束后，把工作变量累加到哈希值 `H[0]-H[7]` 中。所有块处理完后，把8个32位 `H` 值拼接输出为64个十六进制字符。

其中初始哈希值 `INITIAL_HASH[8]` 是前8个质数的平方根小数部分，64个常量 `K[64]` 是前64个质数的立方根小数部分，都来自FIPS 180-4标准。

### 三、什么是彩虹表攻击？盐值怎么防的？

**彩虹表**是一种预计算攻击。攻击者提前把大量常见密码（如 `123456`、`password`、所有6位以下组合等）的SHA-256结果算好存成一张巨大的对照表。拿到系统泄露的哈希值后，直接在表里查找就能反推出原始密码。对于没有盐值的系统，这张表只需要算一次就能攻击所有用户。

**盐值（salt）的作用就是让每个用户的哈希结果独一无二。** 代码中 `generateSalt()` 生成16位随机字符串（从大小写字母+数字中随机选取），在哈希之前拼接到密码后面：

```
存入文件的内容 = SHA256("用户密码" + "随机盐值")，循环1000次
最终存储格式 = "盐值$哈希结果"
```

比如两个用户都用 `123456` 做密码：
- 用户A：`SHA256("123456" + "aB3xK9mP2nR7qW")` → 哈希A
- 用户B：`SHA256("123456" + "fG8jL5tY1hN4cV")` → 哈希B

两次的输出完全不同。攻击者无法用一张通用彩虹表同时攻击两个账户——必须为每个盐值单独算一张表，这让预计算攻击的成本高到不可行。

### 四、为什么迭代1000次？

SHA-256的设计目标是"快"——在普通CPU上，单次SHA-256只需要几百纳秒。这对正常使用是好事（用户登录时很快算完），但对攻击者也是好事——他们用GPU每秒可以尝试数十亿次哈希，暴力破解短密码只需要几秒钟。

**迭代就是人为增加每次尝试的成本。** 代码实现很简单（`SHA256Encrypt` 函数，第91-101行）：

```cpp
std::string SHA256Encrypt(const std::string& password, const std::string& salt, int iterations) {
    std::string currentHash = password + salt;  // 第一次输入：密码+盐值拼接
    for (int i = 0; i < iterations; ++i) {
        currentHash = SHA256::hash(currentHash);  // 每次把上一次的输出作为下一次的输入
    }
    return salt + "$" + currentHash;
}
```

具体过程：
1. 第一次：`currentHash = SHA256("密码" + "盐值")`
2. 第二次：`currentHash = SHA256(第一次的64字符十六进制结果)`
3. 第三次：`currentHash = SHA256(第二次的64字符十六进制结果)`
4. ...重复1000次
5. 最终：存储 `"盐值$第1000次的哈希结果"`

迭代1000次意味着：
- **合法用户**登录时，多算1000次SHA-256，在普通电脑上大约增加1-2毫秒，用户完全感知不到。
- **攻击者**每尝试一个密码猜测，也要多算1000次。如果原本每秒能猜10亿次，现在降到100万次，暴力破解时间扩大1000倍。

1000这个数字是当前课设场景下的合理选择。真实生产系统（如银行、互联网公司）通常用PBKDF2、bcrypt等专用算法，迭代次数在1万到10万之间。

### 五、恒时比较是什么？为什么需要？

代码在 `SHA256Verify` 函数（第103-125行）中：

```cpp
// 恒定时间比较，防止时序攻击
volatile int result = static_cast<int>(calculatedHash.length()) ^ static_cast<int>(storedHash.length());
size_t maxLen = std::max(calculatedHash.length(), storedHash.length());
for (size_t i = 0; i < maxLen; ++i) {
    char c = i < calculatedHash.length() ? calculatedHash[i] : '\0';
    char s = i < storedHash.length() ? storedHash[i] : '\0';
    result |= c ^ s;
}
return result == 0;
```

**时序攻击（Timing Attack）** 的原理：普通的字符串比较 `==` 在发现第一个不匹配的字符时就返回false。攻击者可以构造大量请求，精确测量服务器响应时间：

1. 先尝试各种首字符组合。当首字符猜对时，比较会多执行一个字符的时间，响应会稍微慢一丁点（纳秒级）。
2. 锁定首字符后，再逐位猜第二个字符、第三个字符……
3. 即使每次只有纳秒级的差异，统计几千次请求的平均值后就能分辨出来。

**恒时比较的破解方法：**

1. 先用 `volatile int result` 把长度差异记录下来（`长度异或`）。`volatile` 关键字告诉编译器不要优化这个变量——每次读写都必须真正访问内存，不能缓存到寄存器中做"聪明"的优化。
2. 循环遍历两个字符串的每一位，用 `c ^ s`（异或）比较：相同字符异或结果为0，不同字符异或结果非0。用 `result |=` 累加差异——只要有任何一位不同，result就不为0。
3. 循环一定会跑完 `maxLen` 次，不会提前退出。所以无论密码是否匹配，执行时间都一样。
4. 最后 `return result == 0`：如果所有位都相同，result保持0，返回true；有任一位不同，result非0，返回false。

### 六、验证流程总结

用户登录时，系统做的完整流程：

```
1. 用户输入ID和密码（密码显示为 *）
2. 根据ID在链表中找到对应用户节点
3. 从节点的 storedHash 字段取出 "salt$hash" 格式的字符串
4. 以 '$' 为分隔符，提取出盐值部分
5. 调用 SHA256Encrypt(用户输入的密码, 提取出的盐值, 1000)
   → 内部：把密码和盐值拼接，循环做1000次SHA-256
   → 返回 "盐值$新计算的哈希"
6. 调用 SHA256Verify 进行恒时比较：
   → 比较新计算的 "salt$hash" 和节点里存的 "salt$hash"
   → 逐字符异或，全部为0则匹配成功
7. 检查 isAccountActive 和 isDeleted 标志
8. 全部通过 → 登录成功，loginAttempts归零
   密码错误 → loginAttempts++，达到5次则锁定账户
```

关键点：验证过程中从未"解密"密码。系统永远不存、不传、不解密原始密码，只存和比较哈希结果。

## 附录三：紧急保存机制原理详解（供自读，非答辩内容）

### 一、问题背景：为什么需要紧急保存？

系统的所有数据都在内存里的12条双向链表中，正常退出时main函数会依次调用12个save函数把数据写回txt文件。但如果程序异常终止（用户按Ctrl+C、程序崩溃、操作系统强制关闭），正常退出的save代码根本不会执行，内存中的所有修改就丢了。

C语言标准库提供了**信号（Signal）机制**来处理这种情况。操作系统在终止程序前会发送一个信号，程序可以提前注册一个信号处理函数，在信号到来时执行紧急操作。

### 二、信号注册

代码第102-104行：

```cpp
std::signal(SIGINT, signalHandler);   // 用户按 Ctrl+C
std::signal(SIGABRT, signalHandler);  // 程序调用 abort()（如 assert 失败）
std::signal(SIGTERM, signalHandler);  // 外部发送终止信号（如任务管理器关闭）
```

`std::signal` 是 `<csignal>` 头文件提供的函数，作用是告诉操作系统："当收到指定信号时，不要直接杀掉我的进程，先调用我注册的 `signalHandler` 函数。" 三种信号覆盖了最常见的异常终止场景。

### 三、核心难点：信号处理函数为什么不能直接访问main里的局部变量？

信号处理函数 `signalHandler` 是一个普通的全局函数，它无法直接访问 `main()` 里的局部变量 `adminHead`、`docHead` 等。但保存数据必须拿到这些链表头指针才能遍历链表。

你可能会想：那把它们定义成全局变量不就行了？但这里有个更棘手的问题——**头插法会改变链表头指针的值**。

每次注册新用户时（main.cpp第399-401行）：

```cpp
newAdmin->next = adminHead;         // 新节点的next指向当前头
if (adminHead != nullptr) adminHead->prev = newAdmin;
adminHead = newAdmin;               // adminHead 指向新节点（头插法）
```

`adminHead` 的值一直在变。如果用全局的一级指针 `Admin *g_adminHead` 来记录，它只能在初始化时保存一次 `adminHead` 的值。之后每次头插法改变 `adminHead`，`g_adminHead` 还是老值，紧急保存就会漏掉后来新插入的节点。

### 四、解决方案：双重指针（指针的指针）

代码第30-41行定义了12个全局双重指针：

```cpp
static Admin **g_adminHead = nullptr;      // 指向 "Admin* 类型变量" 的指针
static Doctor **g_docHead = nullptr;
// ... 其余10个同理
```

在main函数加载完所有链表后（第137-140行），把每个局部变量的**地址**赋给对应的双重指针：

```cpp
g_adminHead = &adminHead;    // g_adminHead 存的是 adminHead 这个变量的地址，不是它的值
g_docHead = &docHead;
// ...
```

用图来理解：

```
全局双重指针                    main()里的局部变量              堆上的链表
g_adminHead ──→  adminHead ──→  [节点3] ──→ [节点2] ──→ [节点1] ──→ nullptr
  (存地址0x7ff0)   (地址0x7ff0处      (值0xab30)     (值0xab20)
                   存的值是0xab30)

头插法新增节点4后：
g_adminHead ──→  adminHead ──→  [节点4] ──→ [节点3] ──→ [节点2] ──→ [节点1]
  (地址不变0x7ff0) (值变了0xab40)
```

关键：`g_adminHead` 存的是 `adminHead` 这个变量在栈上的地址（`0x7ff0`），这个地址从头到尾不会变。但 `adminHead` 本身的值（存在 `0x7ff0` 处的内容）会因为头插法而改变。

紧急保存时（第46行）：

```cpp
if (g_adminHead && *g_adminHead) saveAdminData(*g_adminHead, adminIDCount);
```

- `g_adminHead`：检查双重指针本身是否非空（是否已初始化）
- `*g_adminHead`：解引用一次，拿到 `adminHead` 的地址，再取值，得到 `adminHead` 当前的值——也就是最新的链表头
- `saveAdminData(*g_adminHead, ...)`：拿着最新的链表头去遍历保存

这样无论头插法执行了多少次，紧急保存始终能拿到最新的链表头，不会丢失任何节点。

### 五、信号处理函数里的安全约束

C/C++标准规定，信号处理函数中只能调用**信号安全（async-signal-safe）** 的函数。简单来说：

**不能用的：**
- `std::cout` / `std::cin` —— 内部有缓冲区和锁，信号处理中调用可能导致死锁或数据混乱
- `new` / `delete` —— 堆操作不是信号安全的
- `malloc` / `free` —— 同上
- 大部分C标准库函数

**能用的：**
- `write()` / `ReadFile()`（Windows）—— 直接系统调用，无缓冲区
- `_Exit()` —— 不做清理直接退出（不能用 `exit()`，因为 `exit()` 会刷新缓冲区、调用析构函数，可能死锁）

代码中的处理：

1. **输出提示用 `std::cerr`**：`cerr` 默认不带缓冲（`unitbuf`），直接刷新到stderr。虽然严格来说也不是信号安全的，但在这里只用于打印一行提示，实际风险极低。
2. **等待用户按键用 `ReadFile`**：不用 `std::cin.get()`，因为 `cin` 内部有缓冲区和锁。改用Windows API `ReadFile` 直接从标准输入读取1个字节（第75-85行）。
3. **退出用 `_Exit(signum)`**（第92行）：直接终止进程，不调用析构函数、不刷新缓冲区。这是信号处理中唯一安全的退出方式。如果用 `exit()`，它会调用 `atexit` 注册的函数和静态对象的析构函数，可能触发更多不安全的操作。

### 六、"按任意键退出"的完整实现

```cpp
#ifdef _WIN32
    HANDLE hStderr = GetStdHandle(STD_ERROR_HANDLE);       // 获取标准错误输出句柄
    const char *msg = "\n按任意键退出...";
    DWORD written;
    WriteFile(hStderr, msg, strlen(msg), &written, NULL);  // 用WriteFile输出提示（不用cout）

    HANDLE hStdin = GetStdHandle(STD_INPUT_HANDLE);        // 获取标准输入句柄
    FlushConsoleInputBuffer(hStdin);                       // 清空输入缓冲区（丢弃之前的按键）
    DWORD mode;
    GetConsoleMode(hStdin, &mode);                         // 保存当前控制台模式
    SetConsoleMode(hStdin, mode & ~(ENABLE_LINE_INPUT | ENABLE_ECHO_INPUT));  // 关闭行输入和回显
    char buf[1];
    DWORD read;
    ReadFile(hStdin, buf, 1, &read, NULL);                 // 等待用户按任意一个键
    SetConsoleMode(hStdin, mode);                           // 恢复控制台模式
#endif
```

为什么需要"按任意键退出"？因为程序在外部终端窗口运行，如果直接 `_Exit()`，窗口会立即关闭，用户根本看不到"数据已紧急保存"的提示。等待用户按一个键后再退出，让用户有时间看到保存结果。

关闭 `ENABLE_LINE_INPUT` 的原因和登录密码隐藏一样——让 `ReadFile` 不用等用户按回车，按一个键就返回。关闭 `ENABLE_ECHO_INPUT` 是防止按键字符显示在屏幕上（虽然是任意键，但显示一个多余字符不美观）。

### 七、try-catch兜底

main函数第142行开始，整个主循环被 `try` 包裹：

```cpp
try {
    // ... 主循环、正常保存、链表清理 ...
}
catch (const std::exception &e) {
    std::cerr << "\n程序发生异常: " << e.what() << std::endl;
    emergencySave();  // 异常也会触发紧急保存
    return 1;
}
catch (...) {
    std::cerr << "\n程序发生未知异常" << std::endl;
    emergencySave();
    return 1;
}
```

这和信号处理是两套独立的异常保护：
- **信号**：处理来自程序外部的中断（Ctrl+C、系统终止）
- **try-catch**：处理程序内部的异常（越界、空指针、内存不足等）

两种情况都会调用 `emergencySave()`，保证数据不丢失。

### 八、紧急保存的局限性

在答辩中如果老师问到这个机制的缺点，可以如实回答：

1. **不是原子写入**：`saveAdminData` 等函数直接打开文件写入，没有用到"写临时文件→重命名"的原子操作。如果恰好写到一半停电，文件可能只有半截数据。真实系统会用 `rename()` 来保证原子性（先把新数据写到临时文件，写完后 `rename` 替换原文件，rename在大多数文件系统上是原子操作）。
2. **信号处理中调用save函数不是严格安全的**：`std::cerr`、`std::ofstream` 操作理论上不是信号安全的。但在这个课设场景下，紧急保存只做一次就退出，实际出问题的概率极低。
3. **不能处理SIGKILL**：`SIGKILL`（kill -9）无法被捕获，操作系统会立即终止进程，紧急保存不会执行。这种情况任何程序都无法防护。
